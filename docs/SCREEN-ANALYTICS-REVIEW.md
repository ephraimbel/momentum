# Build 44 screen analytics review — 2026-09-07

## Verdict

The first-party pipeline is a reasonable foundation, but the original implementation was not a trustworthy drop-off report. It missed foreground returns without another appearance, could leave dismissed sheets as the current screen, counted active session tails as exits, excluded never-returning open sessions from the inactivity map, and presented independent milestones as a sequential funnel. The fixes and verification results are recorded below. The analytics migration is now applied to production.

## Decisions 1–7

1. **End on background: keep it, name the metric correctly.** These are foreground visits, not conventional 30-minute sessions. A notification reply, phone lock or switching to music ends one; returning starts another. `sessions_per_install` is visit frequency, not retention. The new cohort report uses a later UTC day and matured D1 cohorts for return measures. Background delivery is best-effort: an offline person who never returns can still leave an unsent tail.
2. **Unknown durations: exclude from measured averages and report separately.** Do not impute zero, an average, or the time of next launch. Both abandoned and timed-out endings are lower bounds. `session_shape` now exposes measured counts, visits with no end, recovery counts and the unknown-duration floor. The visit date comes from its original screen events, not a recovery event emitted days later. These are foreground wall-clock durations, not active-attention measurements.
3. **`onAppear`: useful hook, insufficient lifecycle model.** Appearance alone does not cover resuming the same tab or returning from a sheet whose underlying view remained mounted. Presentation owners now register/disappear and restore the surviving surface, foreground returns emit a new view, and consecutive duplicate appearances are suppressed. Progress records its selected segment on entry. The report exposes both per-view and per-visit exit rates, restricted to observed endings. Neither rate proves that the screen caused churn.
4. **Closed enum: keep it.** Stable names and a constrained payload are worth explicit instrumentation. Reflection picks up implementation details, changes under refactors and cannot distinguish meaningful product screens reliably. Add a screen-tracking item to the feature review checklist and maintain navigation regression tests. Names must remain stable; the uniqueness test alone does not freeze the vocabulary. Full random session UUIDs replace eight-character tokens to avoid birthday collisions over a long-lived install.
5. **Batch 20 / cap 500: reasonable starting bounds, not proof of reliability.** At 1,000 daily active installs × 2 visits × 20 screen views, screen views alone are 40,000 rows/day, about 1.2 million/month. Measure row/index bytes and query time before changing limits. The old sink actually sent the entire queue, not batches of 20, could delete newer unsent events when an in-flight queue was trimmed, and dropped all 4xx responses including 429. It now sends bounded batches, removes only sent envelopes, preserves temporary failures and backs off. Service-side enqueue order precedes background flush, with bounded UIKit background execution. Queue overflow still loses the oldest events; telemetry is not lossless or exactly-once. The SQL deduplicates screen sequence/end retries, but older business-event reports can still count delivery retries.
6. **First-party: keep it for this release, but challenge the privacy reasoning.** A third-party analytics processor does not automatically make an app “tracking”; Apple defines tracking by cross-company linkage for advertising/measurement or sharing with data brokers. Conversely, first-party collection is not automatically anonymous: this table's `user_id default auth.uid()` links authenticated events to accounts. Check the existing Product Interaction/User ID disclosures against actual behavior. Session replay is not necessary to identify reach, paths and activation loss, and recording health/fuel/auth screens would require careful exclusion. Do not add it merely to obtain these basic metrics. [Apple privacy definitions](https://developer.apple.com/app-store/app-privacy-details/).
7. **SQL: the partition keys were right; the interpretation and edge cases were not.** `(install_id, session_id)` correctly scopes `lead()`, but its null result means no next observed row, not a confirmed exit. Dedupe and deterministic ordering now precede windows. Digit regex alone did not prevent integer overflow; bounded CASE casts now do. Inactivity uses the latest observed screen even without an end, while recent received events conservatively prevent declaring silence. Acquisition cohorts require a first launch in build 44+, including installs with no screen, rather than conditioning the denominator on survival to `screen_view`. Existing indexes help filtering by name and install/time but cannot remove every sort/aggregate over all history; normal views recompute, and an outer date filter cannot necessarily push through every window. Embedded PostgreSQL executes the queries and EXPLAIN; production cardinality/EXPLAIN ANALYZE remains unverified. Add dated aggregates/materialization when real row counts and latency warrant it. [PostgreSQL window semantics](https://www.postgresql.org/docs/current/functions-window.html).

## Remaining measurement gaps

- **Outcome-linked conversion:** `paywall_convert` may mean a trial; it does not establish trial-to-paid conversion, cancellation or renewal. Join RevenueCat server events to matured acquisition cohorts before explaining trial cancellation.
- **Time to value:** measure time to first completed workout / useful plan / logged meal, then later-day return. A screen exit during recording can be the athlete correctly locking the phone to run.
- **Screen dwell and action outcomes:** paths show transitions, but the current report does not aggregate per-screen dwell or explain camera/plan failures and cancellations. Prefer bounded action/status events to raw text or replay.
- **Segmentation:** acquisition is build-44+ and UTC; reach/path summaries include all instrumented builds and upgrades. Do not use lifetime reach changes as experiment results. Add explicit observation windows/build cohorts for comparisons.
- **Delivery coverage:** launch/screen/end can be lost through offline churn or queue overflow; inferred silence is “no observed activity,” not proof of uninstall. Recovered endings are survivor-biased and must not be labelled crashes. Use Sentry for confirmed crash attribution.
